# 七日任务、贝币小摊刷新与合成掉落

## 七日任务

`data/seven_day.json` 配置七个页签，每页五项。日期表示建议完成阶段，不是开放条件，所有页签从首次启用时同时累计，无七日到期删除。已存在存档从更新后的实际行为开始统计，不根据当前余额、等级反推历史消费或收入。

每项 `id` 唯一，`metric` 为统计项，`target` 为累计目标，`title` 为显示文案，`points` 为领取任务奖励时获得的成长积分，`rewards` 使用统一领奖格式。阶段 `milestones` 配置唯一 `id`、所需累计 `points`、`rewards`。同一任务或阶段只能领取一次，不能靠重复进入面板领取；领奖状态与积分随存档保存。

| metric | 统计范围 |
| --- | --- |
| orders | 成功交付的主棋盘订单 |
| merges | 主棋盘成功合并次数；交换、移动、失败拖拽与活动棋盘不计 |
| xp | 实际获得的经验总量，不随升级归零 |
| cards | 开包获得的卡片张数，重复卡也计数 |
| login_days | 实际出现过的不同自然日数，沿用游戏东八区日界线；缺席日不补算 |
| shell | 实际到账贝币，包括订单、资源领取及各类奖励 |
| amber | 实际到账琥珀，包括资源领取及奖励；初始赠送余额不计 |
| amber_spent | 成功消费的琥珀，不计失败购买或余额同步 |
| paid_cents | 真实支付成功回调的人民币分值；创建/取消/失败订单和 mock 测试支付不计 |

当前每任务 10 分，35 项共 350 分；阶段奖励为 50、100、180、250、300 分。两项支付任务是可选积分来源，其他任务共 330 分，可领取全部阶段奖励。第五个阶段包含两只自选宝箱及 50 琥珀。每页第一项为累计登录任务，对应第 1–7 页分别为累计登录 1–7 天；其他任务可提前完成。旧存档已领取的奖励记录保留。

客户端 `SevenDay` 汇总统计并走 `Rewards.grant` 结算。服务端通过真实业务事件与经济操作记录，上传的客户端任务统计/领奖记录不作为可信来源。领取接口 `/v1/seven-day/claim` 使用统一幂等机制。Python 服务端仍需单独部署；静态网页使用本地存档模式，不提供真实支付。

## 贝币小摊刷新

`data/store_shell.json` 的 `refresh_amber` 当前为 5，比热卖刷新 10 琥珀低。按钮位于原有倒计时横条右侧。成功刷新立即补满所有商品库存，商品品种与贝币售价不变，原本八小时自动补货时间不变。余额不足不重置库存。联机接口 `/v1/shop/shell/refresh`，重复同一请求不会再次扣费。刷新消费计入七日任务的琥珀消费。

## 合并掉贝币

`data/rules.json`：`merge_coin_chance` 当前为 0.05，`merge_coin_item` 当前为 `shell_1`。主棋盘每次成功合并独立判定一次，掉出可继续合并的一级贝币，放入最近空位，不直接加入顶部余额。新手引导期间和没有空位时不掉落。失败拖拽、交换、生产和活动棋盘均不触发。

每次合并生成随机事件 ID，以 ID 的 SHA-256 前 8 个十六进制字符除以 2^32 作为抽样值，客户端与服务端得出相同结果。服务端仅在同一事件首次处理时增加物品额度，重试不重新抽奖。主棋盘沿用原有客户端模拟/服务端经济核对结构，并非逐步由服务端重演棋盘。

## 储物洞

容量不设上限，初始 5 格，列表每行 5 格、行距 144，支持拖拽和滚轮滚动。界面仅复用可见区域附近的 30 个格子控件，大容量不会创建大量隐藏按钮。

`data/rules.json` 配置 `storage_initial`、`storage_expand_price`、`storage_expand_step`，当前为 5、50、10。下一格价格 = 50 + (当前容量 - 5) × 10；例如从 5 扩到 6 花 50，从 6 扩到 7 花 60，已有 10 格的旧存档下一格花 100。客户端与服务端读取同一配置。余额不足不扣费、不涨容量或价格。
